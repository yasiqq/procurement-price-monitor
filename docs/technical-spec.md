# 1. Общие положения

## 1.1. Название проекта

**Procurement Price Monitor**

Репозиторий: `github.com/yasiqq/procurement-price-monitor`

## 1.2. Назначение системы

Procurement Price Monitor — клиент-серверная аналитическая платформа для сбора рыночных котировок сырьевых товаров, хранения и обработки данных, а также оценки эффективности закупок предприятия.

Система должна сопоставлять закупочные цены компании с рыночными ориентирами, рассчитывать отклонения и помогать выявлять невыгодные закупки.

**Главный результат проекта — не сайт с биржевыми графиками, а система аналитики закупок, основанная на воспроизводимом процессе обработки данных.**

## 1.3. Цель разработки

Создать работающую систему, объединяющую:

1. Сбор данных из внешних источников.
2. ETL-процессы на Python.
3. Многоуровневое хранение в PostgreSQL.
4. Очистку и проверку качества данных.
5. Генерацию синтетических закупок предприятия.
6. Аналитические витрины SQL.
7. REST API на FastAPI.
8. Клиентское приложение на React.
9. Базовое тестирование и документирование.

Проект должен демонстрировать практические навыки Data Engineering и интеграции компонентов полноценной аналитической платформы.

## 1.4. Основной принцип разработки

**Сначала данные, затем интерфейс.**

Приоритет имеет один работающий сквозной сценарий:

`Источник → RAW → CORE → MART → FastAPI → React`

Широта функциональности не должна достигаться за счёт незавершённой базовой архитектуры.

# 4. Исходные данные

## 4.1. Перечень источников

| Данные | Инструмент | Источник | Формат | Единица | Валюта |
|---|---|---|---|---|---|
| Золото | `GLDRUB_TOM` | MOEX ISS | JSON | грамм | RUB |
| Медь | `COPPER` | MOEX CSV | CSV | тонна* | USD* |
| Алюминий | `ALUM` | MOEX CSV | CSV | тонна* | USD* |
| Доллар США | `R01235` | ЦБ РФ | XML | 1 USD | RUB |

\* Для меди и алюминия единицы измерения и валюта приняты как рабочее предположение. **Перед окончательной реализацией аналитических расчётов необходимо подтвердить их по спецификации источника MOEX.**

## 4.2. Исторический период

Начальная дата для всех источников — **08.10.2024**.

Причина выбора: с этой даты начинается доступный набор CSV-котировок меди и алюминия.

Первоначальный объём — примерно два года данных.

Конечная дата должна задаваться параметром загрузчика. При дальнейшем обновлении допускается загрузка новых доступных торговых дат.

## 4.3. Общие требования к источникам

Каждый загрузчик должен:

- Получать данные из определённого источника.
- Проверять корректность ответа.
- Сохранять необходимые исходные поля.
- Не создавать дубликаты при повторном запуске.
- Корректно обрабатывать ошибки.
- Позволять проверить количество загруженных строк.
- Не подменять отсутствующие рыночные данные выдуманными значениями.

Загрузчики разных источников должны быть логически разделены.

# 5. MOEX ISS — золото

## 5.1. Источник

Используется исторический API Московской биржи.

Параметры:

- Engine: `currency`.
- Market: `selt`.
- Board: `CETS`.
- Security: `GLDRUB_TOM`.

Endpoint:

`https://iss.moex.com/iss/history/engines/currency/markets/selt/boards/CETS/securities/GLDRUB_TOM.json`

## 5.2. Поля источника

- `BOARDID`
- `TRADEDATE`
- `SHORTNAME`
- `SECID`
- `OPEN`
- `LOW`
- `HIGH`
- `CLOSE`
- `NUMTRADES`
- `WAPRICE`

Все десять полей должны сохраняться в RAW.

Для основной аналитики используется **`CLOSE`**.

`WAPRICE` сохраняется в RAW, но не заменяет цену закрытия.

## 5.3. Пагинация

MOEX ISS возвращает историю постранично.

Необходимо использовать:

- `history.columns`
- `history.data`
- `history.cursor`

Поля курсора:

- `INDEX`
- `TOTAL`
- `PAGESIZE`

Для получения следующих страниц применяется HTTP-параметр `start`.

Загрузчик должен собирать полный набор данных, не ограничиваясь первой страницей.

## 5.4. Структура результата Python

Функция чтения MOEX ISS должна возвращать список словарей:

`list[dict]`

Каждый словарь соответствует одной котировке.

Названия полей должны определяться через `history.columns`, а не через жёстко прописанные позиции значений.

Это особенно важно, поскольку порядок `OPEN`, `LOW`, `HIGH`, `CLOSE` в ISS отличается от порядка полей в CSV.

## 5.5. Обработка HTTP-ошибок

Необходимы:

- Тайм-ауты.
- Проверка HTTP-статуса.
- Проверка структуры JSON.
- Обработка ошибок соединения.
- Предсказуемая реакция на пустую страницу.

Повторные попытки запросов допускается добавить без усложнения общей архитектуры.

# 6. MOEX CSV — медь и алюминий

## 6.1. Источник

Исторические CSV-файлы, полученные с сайта MOEX.

Локальное размещение: каталог `data/`.

Исходные CSV не должны включаться в Git-репозиторий.

## 6.2. Структура CSV

Используются поля:

- `<TICKER>`
- `<PER>`
- `<DATE>`
- `<TIME>`
- `<OPEN>`
- `<HIGH>`
- `<LOW>`
- `<CLOSE>`
- `<VOL>`

Разделитель: `;`.

Дата имеет формат `YYYYMMDD`.

## 6.3. Требования

- Чтение одного или нескольких CSV.
- Корректный разбор заголовков.
- Объединение данных меди и алюминия.
- Сохранение в RAW.
- Проверка дат и цен.
- Преобразование в CORE.
- Идемпотентность повторной загрузки.

На начальном этапе используются готовые непрерывные ряды `COPPER` и `ALUM`.

**Самостоятельная склейка фьючерсных контрактов не реализуется в MVP.**

# 7. Центральный банк РФ — USD/RUB

## 7.1. Источник

Официальный сервис ЦБ РФ для получения динамики валютного курса.

Код USD: `R01235`.

Источник данных: `cbr.ru`, XML API `XML_dynamic.asp`.

## 7.2. Особенности XML

Необходимо учитывать:

- Даты в формате `DD.MM.YYYY`.
- Десятичную запятую.
- Кодировку `windows-1251`.
- Поля `Nominal`, `Value`, `VunitRate`.
- Отличие календаря публикации курсов от торгового календаря MOEX.

## 7.3. Требования

Загрузчик должен получать курс, сохранять исходные значения в RAW и преобразовывать их в числовые значения в CORE.

Для аналитических расчётов должен использоваться курс, выражающий стоимость **одного доллара США в рублях**.

При отсутствии курса на определённую дату используется последний доступный курс, дата которого не превышает дату расчёта.

# 8. Архитектура хранения данных

Используется PostgreSQL 16 с тремя основными схемами:

`raw → core → mart`

## 8.1. RAW — исходные данные

### Назначение

Сохранять значения максимально близко к исходному формату.

На этом уровне не выполняется окончательная аналитическая очистка.

Допускается добавление технических полей, например идентификатора записи и времени загрузки.

### Таблицы

**`raw.moex_csv_quotes`**

Содержит исходные CSV-котировки меди и алюминия.

**`raw.moex_history`**

Содержит исходные котировки золота из MOEX ISS.

Поля:

- `id`
- `BOARDID`
- `TRADEDATE`
- `SHORTNAME`
- `SECID`
- `OPEN`
- `LOW`
- `HIGH`
- `CLOSE`
- `NUMTRADES`
- `WAPRICE`
- `loaded_at`

Для текущего источника принято ограничение:

`UNIQUE (TRADEDATE, SECID)`

При подключении других режимов торгов необходимо пересмотреть уникальность с учётом `BOARDID`.

**`raw.cbr_rates`**

Предусматривается для исходных валютных данных ЦБ РФ.

### Ошибочные записи

Некорректные данные должны сохраняться или регистрироваться таким образом, чтобы можно было определить источник, причину отклонения и исходную запись.

Уже реализованный механизм для CSV должен использоваться как образец.

---

## 8.2. CORE — очищенные данные

### Назначение

CORE содержит данные в корректных типах, пригодные для SQL-аналитики.

Основные требования:

- Тип `DATE` для дат.
- Тип `NUMERIC` для цен и количеств.
- Ссылочная целостность.
- Уникальность по бизнес-ключам.
- Проверка допустимых значений.
- Отсутствие дублирования.

### `core.commodities`

Справочник сырья.

Логическая структура:

- `id`
- `name`
- `ticker`
- `source`
- `unit`
- `currency`

Справочник содержит три товара.

При необходимости существующая структура расширяется миграциями, без пересоздания уже заполненных таблиц.

### `core.market_quotes`

Таблица рыночных котировок.

Текущие фактические поля проекта:

- `commodity_id`
- `trade_date`
- `price`

Цена представляет собой `CLOSE` в исходной валюте и единице измерения инструмента.

Уникальность:

`UNIQUE (commodity_id, trade_date)`

При повторной обработке изменённые цены должны обновляться, а неизменённые не должны вызывать лишних записей.

### `core.fx_rates`

Планируемая таблица курсов валют:

- `id`
- `currency`
- `rate_date`
- `rate`

Уникальность:

`UNIQUE (currency, rate_date)`

Курс должен быть рассчитан на одну единицу валюты.

### `core.suppliers`

Планируемый справочник поставщиков.

Минимальные поля:

- `id`
- `name`

Для MVP требуется **3–5 поставщиков**.

### `core.purchases`

Планируемая таблица закупок:

- `id`
- `purchase_date`
- `commodity_id`
- `supplier_id`
- `quantity`
- `unit_price`
- `currency`

Требования:

- `commodity_id` ссылается на `core.commodities`.
- `supplier_id` ссылается на `core.suppliers`.
- `quantity` положительное.
- `unit_price` положительное.
- Для MVP `currency = RUB`.
- Цена закупки выражена в рублях за принятую единицу соответствующего сырья.

## 8.3. MART — аналитические витрины

### Назначение

MART формирует готовые данные для аналитики и FastAPI.

Основной механизм первой версии — **SQL VIEW**.

Применять отдельное хранилище, dbt или сложную систему трансформаций не требуется.

### Обязательные витрины

**`mart.purchase_vs_market`**

Сопоставляет закупки с рыночными котировками и курсом валюты.

**Витрина месячных отклонений**

Группирует результаты сравнения по месяцам и сырью.

**Витрина поставщиков**

Группирует результаты сравнения по поставщикам.

Точные имена дополнительных представлений определяются при разработке SQL.

# 9. Бизнес-правила

Это обязательный раздел. Правила должны одинаково применяться при построении SQL-витрин, API и отображении данных на клиенте.

## 9.1. Рыночная цена

Для всех трёх инструментов рыночным ориентиром является цена закрытия `CLOSE`.

Другие показатели не используются вместо `CLOSE` без явного изменения ТЗ.

## 9.2. Валюта

В `core.market_quotes` цена хранится в исходной валюте.

В `mart` цена приводится к рублям.

Для золота:

`market_price_rub = CLOSE`

Для меди и алюминия:

`market_price_rub = CLOSE × USD_RUB`

Конвертация производится **один раз в MART**.

## 9.3. Единицы измерения

- Золото — рубли за грамм.
- Медь — рубли за тонну.
- Алюминий — рубли за тонну.

Пересчёт граммов в тонны между разными видами сырья не требуется.

Цена закупки и рыночная цена одного товара должны иметь одинаковую единицу измерения.

## 9.4. Несовпадение календарей

Если котировка на дату закупки отсутствует, используется последняя доступная котировка **с датой не позднее даты закупки**.

Аналогично выбирается курс ЦБ РФ.

Нельзя использовать котировку или курс из будущего относительно даты закупки.

Дата реально использованного рыночного ориентира должна быть доступна для проверки.

## 9.5. Недоступные данные

Если нет подходящей предыдущей котировки или курса, расчёт должен возвращать отсутствие результата, а не произвольное значение.

Такая закупка должна быть явно обозначена как нерассчитанная.

## 9.6. Изменение исторических котировок

ETL должен поддерживать повторные запуски без дубликатов.

Если источник исправил историческую цену, целевое поведение — иметь возможность обновить её в RAW и затем в CORE.

Использование `DO NOTHING` допустимо как промежуточный этап загрузчика, но не должно препятствовать выполнению этого требования в окончательной версии.

# 10. Генерация закупок предприятия

## 10.1. Назначение

Поскольку реальные корпоративные закупки недоступны, система должна использовать **реалистичные синтетические закупки**, построенные на основе настоящих рыночных котировок.

Данные должны быть полезными для проверки аналитики, а не просто случайными числами.

## 10.2. Объём

Сгенерировать приблизительно **2 000–5 000 записей**.

Использовать 3–5 поставщиков.

## 10.3. Принцип формирования цен

Базовая идея:

`Закупочная цена = рыночная цена × (1 + наценка поставщика) + шум + сезонная составляющая + возможная аномалия`

Все составляющие должны рассчитываться в согласованных единицах.

Используемые параметры должны быть задокументированы.

## 10.4. Поставщики

Для генератора предусматриваются разные модели поведения.

Примеры:

- Стабильный поставщик: средняя наценка около +1%.
- Дорогой поставщик: средняя наценка около +8%.
- Нестабильный поставщик: значительные колебания вокруг рынка, например ±10%.
- Сезонный поставщик: отклонение зависит от периода года.

Эти параметры являются ориентиром для модели генератора, а не фактическими характеристиками реальных компаний.

## 10.5. Аномальные закупки

Часть закупок — ориентировочно **1–2%** — должна содержать специально созданные аномалии.

Пример: закупочная цена выше рыночного ориентира на 25–40%.

Аномалии необходимы для проверки механизма обнаружения невыгодных закупок.

## 10.6. Воспроизводимость

Генератор обязан использовать фиксированный случайный `seed`.

При одинаковых входных рыночных данных и параметрах генерации результат должен быть воспроизводимым.

Повторный запуск не должен бесконтрольно создавать новые дубликаты.

## 10.7. Контрольная информация

Генератор должен позволять проверить, соответствуют ли результаты аналитики заложенным наценкам и аномалиям.

При необходимости допускается технический флаг `is_anomaly`, используемый для тестирования.

Наличие этого флага не должно подменять фактический аналитический расчёт.

# 11. Аналитические расчёты

## 11.1. Абсолютное отклонение

`deviation_rub = purchase_price_rub - market_price_rub`

Интерпретация:

- Положительное значение — закупка дороже рыночного ориентира.
- Отрицательное значение — закупка дешевле.
- Ноль — цены равны.

## 11.2. Процентное отклонение

`deviation_pct = deviation_rub / market_price_rub × 100`

Процент рассчитывается только при наличии положительной рыночной цены.

## 11.3. Финансовый эффект

`financial_effect_rub = deviation_rub × quantity`

При положительном результате получаем условную переплату.

При отрицательном — условную экономию.

Результат является сравнением с выбранным рыночным ориентиром, а не бухгалтерским подтверждением убытка.

## 11.4. Обязательные аналитические вопросы

Система должна позволять получить ответы на следующие вопросы.

**Анализ по сырью**

На сколько процентов в среднем закупки золота, меди и алюминия дороже или дешевле рынка?

**Анализ поставщиков**

Какой поставщик чаще закупает дороже рыночной цены и у какого поставщика отклонения наиболее значительны?

**Анализ по месяцам**

Как меняется отклонение закупочных цен от рынка во времени? Видны ли тренды и сезонные особенности?

**Влияние курса доллара**

Как изменение USD/RUB влияет на рублёвую рыночную стоимость меди и алюминия?

**Поиск аномалий**

Какие закупки превышают рыночную цену более чем на заданный порог `N%`?

**Финансовый эффект**

Какова суммарная условная переплата за выбранный период, по товару или поставщику?

## 11.5. Агрегирование

При группировке необходимо корректно различать:

- Среднее процентное отклонение по отдельным закупкам.
- Суммарный финансовый эффект.
- Количество закупок.
- Количество и долю закупок выше рынка.
- Среднюю величину положительного отклонения.

Средняя переплата и суммарная переплата — разные показатели; они не должны смешиваться.

# 13. Клиентская часть — React

## 13.1. Назначение

Клиентское приложение должно предоставлять пользователю понятный интерфейс для изучения рынка, сравнения закупок и оценки поставщиков.

## 13.2. Общая структура MVP

Предусматриваются **три основных экрана**.

Это ограничение намеренное: первая версия не должна превращаться в большой интерфейсный проект в ущерб Data Engineering.

### Экран 1. Рынок и закупки

Основной экран для исследования цен и отдельных закупок.

**Функциональность:**

- Выбор товара.
- Выбор периода.
- График изменения рыночной цены.
- Отображение закупочных цен.
- Сравнение рынка и закупок во времени.
- Таблица закупок за период.
- Абсолютные и процентные отклонения.
- Поиск закупок выше заданного порога.
- Просмотр даты использованного рыночного ориентира.

**График:**

Ось X — дата.

Ось Y — цена в рублях за соответствующую единицу сырья.

Рыночные и закупочные цены должны быть визуально различимы.

Для золота, меди и алюминия должна корректно отображаться единица измерения.

### Экран 2. Отклонения по месяцам

Экран анализа динамики эффективности закупок.

**Функциональность:**

- Выбор товара.
- Выбор периода.
- График среднего процентного отклонения по месяцам.
- Показатель суммарной условной переплаты.
- Таблица помесячных агрегатов.
- Возможность увидеть изменение показателей во времени.
- Сопоставление динамики меди и алюминия с изменением курса USD/RUB.

Пользователь должен понимать, когда закупки систематически становились дороже рынка.

### Экран 3. Рейтинг поставщиков

Экран сравнительной оценки поставщиков.

**Функциональность:**

- Таблица 3–5 поставщиков.
- Количество закупок каждого поставщика.
- Среднее процентное отклонение.
- Доля закупок выше рынка.
- Суммарная условная переплата.
- Количество аномальных закупок.
- Сортировка по выбранному показателю.
- Фильтрация по товару и периоду.

**Цель:** показать, какие поставщики наиболее выгодны, а какие систематически формируют более высокие закупочные цены.

## 13.3. Навигация

Между тремя экранами должна быть простая навигация.

Пользователь должен понимать, какой раздел открыт.

Допускается единая шапка приложения с названием проекта и основными фильтрами.

## 13.4. Графики

В MVP допустимо использовать Recharts или Chart.js.

Графики должны поддерживать:

- Подписи осей.
- Подсказки при наведении.
- Легенду.
- Отображение валюты и единиц.
- Обновление при изменении фильтров.
- Корректную обработку отсутствующих данных.

Графики строятся из данных FastAPI.

`pandas` может применяться для внутреннего анализа и проверки ETL, но **не заменяет React-визуализацию**.

## 13.5. Таблицы

Таблицы должны поддерживать:

- Читаемые заголовки.
- Форматирование дат.
- Форматирование чисел.
- Сортировку.
- Фильтрацию.
- Понятное отображение пустого результата.

Большие наборы данных не должны без необходимости целиком загружаться в браузер.

## 13.6. Индикация отклонений

Интерфейс должен визуально различать:

- Закупки выше рынка.
- Закупки ниже рынка.

- Аномальные закупки.

Одного цвета недостаточно: статус должен иметь также текстовое или числовое обозначение.

## 13.7. Обработка ошибок

Клиент должен отображать:

- Состояние загрузки.
- Ошибки API.
- Отсутствие данных.
- Некорректные фильтры.

Не допускается показывать тестовые или фиктивные значения как реальные результаты API.

# 14. ETL-процессы и качество данных

## 14.1. Структура процессов

Для каждого источника используются отдельные этапы:

1. Получение данных.
2. Загрузка в RAW.
3. Проверка качества.
4. Перенос корректных записей в CORE.
5. Использование данных в MART.

Разделение должно быть отражено в структуре Python-модулей и SQL-файлов.

## 14.2. Идемпотентность

Повторный запуск не должен создавать логические дубликаты.

Применяются:

- Ограничения `UNIQUE`.
- `ON CONFLICT`.
- Транзакции.
- Контролируемое обновление изменённых значений.

## 14.3. Контроль качества

Проверки должны охватывать:

- Некорректные даты.
- Некорректные числовые значения.
- Нулевые и отрицательные цены.
- Неизвестные тикеры.
- Дубликаты.
- Отсутствующие обязательные поля.

Отклонённые записи должны быть доступны для анализа.

## 14.4. Пропущенные даты

Отсутствие торгов в выходные и праздники не является ошибкой само по себе.

Отсутствующую котировку нельзя автоматически считать нулевой.

Для аналитических сопоставлений применяется правило последней доступной котировки на дату или ранее.

## 14.5. Логирование

Предусмотреть фиксацию:

- Источника.
- Времени запуска.
- Количества полученных записей.
- Количества обработанных записей.
- Количества отклонённых записей.
- Успешности выполнения.
- Ошибок.

Для MVP достаточно стандартного Python `logging` и понятного консольного вывода.

## 14.6. Автоматическое обновление

В конце основного этапа разработки желательно добавить простой запуск по расписанию.

Допустимые варианты:

- Cron.
- APScheduler.
- Планировщик задач ОС.

Airflow и Prefect для этого не требуются.

# 19. Критерии приёмки MVP

Проект считается завершённым, когда выполнены все следующие условия:

1. PostgreSQL запускается локально через Docker Compose.
2. Структура базы воспроизводится с помощью миграций.
3. Рыночные котировки всех трёх товаров находятся в CORE.
4. Курсы USD/RUB находятся в CORE.
5. Повторный запуск ETL не создаёт дубликаты.
6. Некорректные исходные записи не попадают в CORE как корректные.
7. Созданы 3–5 поставщиков.
8. Генератор создаёт 2–5 тысяч воспроизводимых синтетических закупок.
9. MART правильно сопоставляет закупки с рынком и валютным курсом.
10. Отклонения и финансовые эффекты проходят контрольные проверки.
11. API предоставляет котировки, закупки и агрегированную аналитику.
12. React содержит три основных аналитических экрана.
13. Пользователь может выбрать товар и период.
14. Пользователь может определить невыгодные и аномальные закупки.
15. Пользователь может сравнить поставщиков.
16. Проект запускается по документированной инструкции.
17. В GitHub присутствуют исходный код, миграции, документация и описание демонстрации.

# 20. Демонстрационный сценарий

Пользователь открывает Procurement Price Monitor.

На первом экране выбирает **медь** и интересующий период.

Приложение отображает рыночные цены, приведённые к рублям, и синтетические закупки предприятия.

Пользователь выбирает одну закупку и видит:

- Дату закупки.
- Поставщика.
- Количество.
- Закупочную цену в рублях.
- Рыночную котировку.
- Применённый курс USD/RUB.
- Даты использованных рыночных данных.
- Процент отклонения.
- Рассчитанную условную переплату или экономию.

На втором экране пользователь изучает динамику отклонений по месяцам.

На третьем — сравнивает поставщиков и определяет, кто чаще закупает дороже рынка.

Все отображаемые результаты формируются на основании данных PostgreSQL, обработанных ETL и предоставленных через FastAPI.

# 21. Правила дальнейшей работы над проектом

Этот раздел фиксирует учебный формат разработки.

**Роль пользователя:** разработчик проекта.

**Роль ассистента:** научный руководитель и наставник по Data Engineering, не исполнитель.

Основные правила:

1. Перед новым шагом объяснять его цель и задавать 1–2 вопроса на понимание.
2. Сначала давать направление, затем более конкретные подсказки.
3. Не писать готовый код для файлов проекта без явного запроса пользователя после самостоятельной попытки.
4. При Code Review указывать ошибку, её причину и принцип исправления.
5. Давать небольшие учебные шаги, а не перегружать сразу всем планом.
6. Для каждого шага определять способ самостоятельной проверки.
7. Сохранять приоритет Data Engineering над второстепенными улучшениями.
8. Не добавлять технологии вне MVP без обоснованной необходимости.
9. Не объявлять этап выполненным без результата проверки.
10. При расхождении между новой идеей и настоящим ТЗ сначала обсуждать изменение требований.

# 22. Приоритет и изменение требований

**Настоящее ТЗ является базовым документом проекта Procurement Price Monitor версии 1.0.**

При дальнейшей разработке следует придерживаться следующего порядка:

- Утверждённые бизнес-правила и архитектура из настоящего ТЗ.
- Фактическое состояние кода и базы данных, подтверждённое проверками.
- Документация в репозитории.
- Новые решения, явно согласованные в ходе разработки.

Любое существенное изменение состава источников, валютных правил, модели данных, аналитических формул или объёма клиентской части должно фиксироваться в новой редакции ТЗ либо в `docs/scope.md`.

**Ключевой принцип проекта: сначала достоверные данные и правильная аналитика, затем API и интерфейс, затем дополнительные возможности.**
